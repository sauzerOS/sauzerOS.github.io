hokuto package manager

Package manager written in Go with minimal optional external dependencies:

  • tar and zstd: creating and installing packages; built-in fallbacks cover them only when hokuto runs as root
  • wget: fallback download client

The package manager is fully functional without any external dependencies if executed as root.

hokuto function

Package Structure

A recipe is a directory with these files:

build
bash file with build instructions
checksums
b3sums of source files
depends{.subpackage}
dependencies, one per line, optionally tagged (see Dependency tags)
equivalents
(repository root) mutually exclusive, dependency-compatible package pairs, one pair per line as upstream-package replacement-package. Either installed package satisfies an unconstrained dependency on the other. Installing one replaces the other, and generated library dependencies use an ordered replacement | upstream alternative for replacement packages. Version-constrained dependencies remain exact. The relevant pair is embedded in built packages so replacement also works when installing exclusively from a binary mirror. Replacing a package also replaces the installed packages that depend on it and are one side of a pair themselves: installing xorg-server over xlibre installs xf86-input-libinput in place of xlibre-xf86-input-libinput
options
build options (see Option tags)
bump-follows
name of a package whose version this recipe shares (for example linux in linux-live). hokuto bump, including auto-bump, bumps the recipe to the same version in the same push whenever that package gets a new version; a revision-only bump leaves it alone
files
local package files
libdeps.ignore{.subpackage}
ignore dependency during auto dependency resolution
post-install
bash script executed after package install
.sources
source links with substitutions (see .sources substitutions)
sources
source links with substitutions replaced with actual links, for repology parsing (see sources line options)
version
version revision

Dependency tags (depends)
pkgname
runtime/build dependency
pkgname==17.*
require any release from major version 17
pkgname make
build dependency
pkgname makeopt
optional binary-only build dependency. Hokuto uses an installed package or installs an available binary version for the build, but continues without it when no binary is available. Packages installed only for the build are removed afterward
pkgname optional
package will be automatically rebuilt once the dependency is available (solves circular deps)
pkgname runtime
runtime only dependency
pkgname suggest "comment"
suggested optional dependency, offered after the package is installed. On an architecture whose packages are cross built (aarch64), a suggestion is only offered when a package was published for it or its recipe is prepared for cross builds
pkgname post-install
needed only by the package's post-install script (e.g. gawk post-install for a hook that runs awk, dracut post-install for a kernel). Hokuto installs it just before the script runs if it is missing, and removes it again afterwards unless another package needs it; it is neither a runtime nor a build dependency
pkgname rebuild
forces rebuild of package even if already installed, only enabled with -rebuilds build command flag
pkgname cross
cross (arm64) runtime dependency, e.g. aarch64-zlib-ng cross as a dependency of file pulls in aarch64-zlib-ng whenever aarch64-file is built/installed, and it stays a real (always-verified) dependency afterward, same as a plain dependency line but scoped to cross builds
pkgname cross make
cross (arm64) build-time-only dependency; only needed while building the cross target, not required once it's installed (e.g. aarch64-gcc cross make)
pkgname crossnative
like cross, but skipped when building the cross-system toolchain itself (-cross=arm64,system)
pkgname crossnative make
like cross make, but skipped when building the cross-system toolchain itself
pkgname nocross
runtime dependency of the native build only. It is not recorded in the depends of a cross-built package, since a cross build usually enables a smaller feature set and the target would otherwise demand packages it neither needs nor has
== <> => <= version
dependency version constraints (eg ffmpeg<=7.2.0). hokuto can build older versions by fetching the package from the repo git history
package1 | package2
hokuto will prompt which dependency to use

Prefixed vs bare cross dependencies. A cross dependency whose name carries the target arch prefix (aarch64-gcc cross make, aarch64-libelf cross make) is a target artifact, built for the target and installed into the sysroot. A cross dependency with a bare name (mercurial cross make, cmake cross make) is a host tool the cross build needs and is built/installed natively — use this when there is no sensible aarch64-* counterpart. A cross dependency naming a different architecture (x86_64-gcc cross make while targeting arm64) is ignored, so one depends file can list several targets.

Cross builds only honor cross dependencies. Under -cross=<arch> (with or without ,system) every dependency line that is neither tagged cross/crossnative nor already carries the target arch prefix (aarch64-*) is ignored, including plain make dependencies. Those lines describe the native build of the package; a cross build must declare what it needs explicitly. So a recipe that needs e.g. pahole for both builds lists it twice: pahole make for native and pahole cross make for cross.

Kernel Module Packages

Kernel modules only load into the exact kernel release they were built for, and several kernels can be installed side by side (linux, linux-cachyos). A recipe with kmod in its options is therefore never built or installed under its own name but once per kernel, as an instance named after the kernel package: nvidia-open~linux, nvidia-open~linux-cachyos. Instances of different kernels are installed at the same time; config files they both ship (e.g. /etc/modprobe.d) are shared without a conflict prompt.

  • hokuto install nvidia-open / hokuto build nvidia-open: with one kernel installed its instance is used; with several, hokuto asks which kernel(s). -y or a non-interactive run takes all of them. An instance can also be named directly: hokuto build nvidia-open~linux
  • For an instance build hokuto installs the kernel's headers package (<kernel>-headers) if its build tree is missing, and sets $HOKUTO_KERNEL_DIR (the build tree, /usr/lib/modules/<release>/build), $HOKUTO_KERNEL_RELEASE and $HOKUTO_KERNEL_PACKAGE. The recipe must build against these, not /usr/src/linux or the running kernel; a package that ships modules for any other release is rejected
  • The release is recorded in the package (kernel_release, kernel_package in pkginfo). Installing refuses a binary built for a release other than the one its kernel has installed now, e.g. a mirror build from before the last kernel update; rebuild the instance instead
  • hokuto.rebuild keeps listing the plain name (linux-cachyos nvidia-open); the rebuild runs for the instance of the kernel that triggered it
  • A module package installed before kernel tracking (plain nvidia-open) is migrated automatically: hokuto update updates it as the instance for the kernel its files were built for (or the only installed kernel) and removes the plain package once that instance is installed; hokuto install nvidia-open offers to remove it
Cross Build Support

Cross building a recipe that was never adapted for it rarely fails outright. Configure scripts fall back to host defaults, the build picks up the host's headers and libraries, and the result looks like a package right up until something links against it or it is installed on the target. Hokuto therefore refuses such a build instead of producing one.

A recipe counts as prepared for cross builds when any of these is true:

  • its options file contains cross
  • its build script branches on the cross environment, that is it mentions CROSS_PREFIX, HOKUTO_CROSS or CROSS_COMPILE outside a comment
  • its depends file declares cross or crossnative dependencies

Both of the last two are needed because neither is sufficient on its own: low level packages such as brotli and gmp handle CROSS_PREFIX but have too few dependencies for any of them to be marked cross, while shadow and linux-rpi4 carry cross dependencies without naming hokuto's variables in their script.

options wins over what the recipe looks like, in both directions: cross marks a recipe that needs no changes (an arch-independent or data-only package, for instance), and nocross holds one back that would otherwise pass. The check applies to both -cross=<arch> and -cross=<arch>,system, and not to plain build dependencies that are compiled natively during a cross session.

Building an unprepared recipe anyway, while adapting it

HOKUTO_ALLOW_UNCONFIGURED_CROSS=1 hokuto build -cross=arm64 pkgname

gobject-introspection cannot scan a library built for another architecture, so cross builds disable introspection. A -cross=<arch> build of a recipe whose native build depends on gobject-introspection then copies the typelibs, .gir files and Vala bindings that its outputs lack from the published x86_64 package of the same name and version: both architectures are LP64 with the same type sizes and alignment, which is all the typelib's layout data depends on. The x86_64 package has to be built first; without it the output goes without, with a warning. Cross-system (,system) builds are not given any.

Just as a native build installs any missing base-devel packages first, a cross build (-cross=arm64 or -cross=arm64,system) also installs the missing members of the aarch64-base-devel metapackage, the cross toolchain. A toolchain package that the build itself produces is not installed beforehand, so the toolchain can be built from scratch. -no-devel skips both, and the nodevel/binary options apply as for native builds.

hokuto cross-sync

hokuto cross-sync keeps the aarch64 packages on the binary mirror in step with the recipes. It compares the mirror index with the recipes' current versions, lists the packages that have no package of that version on the mirror or in the local binary cache, and builds the ones picked from the list.

  • hokuto cross-sync: native aarch64 packages. Only recipes that already have an aarch64 package on the mirror are checked; they are built with -cross=arm64
  • hokuto cross-sync -system: the cross-system packages, the aarch64-* toolchain and sysroot packages. Every aarch64-* package on the mirror is checked against its recipe (aarch64-gcc against gcc) and built with -cross=arm64,system. Packages whose recipe is gone are skipped. Nothing needs to be installed on the host or build container for this, so the toolchain stays current without being kept installed
  • -i builds at idle priority and -jN builds N packages in parallel, as with hokuto build; -no-install skips the offer to install the built -system packages on the build host (native aarch64 packages are never installed there)
Binary Packages

A binary package is an ordinary .tar.zst, readable by tar --zstd -xf and any zstd implementation. It is compressed as a series of independent zstd frames rather than one, which is what lets hokuto decompress it on several cores when installing; a single frame can only ever be decoded by one.

The frame size is chosen from the size of the package so that it lands on about half the machine's cores, clamped between 32 MiB and 256 MiB. Cutting the stream costs a little compression ratio, because matches can no longer reach back across a frame boundary, and the clamps keep that in the region of a fraction of a percent for large packages. A package small enough to fit in one frame is compressed exactly as it was before.

Installing unpacks into a staging directory and then moves the tree into place. When staging and the target root are on the same filesystem, that move is done with hard links: mode, ownership, timestamps, xattrs and ACLs come along with the inode, files hard linked to each other inside the package stay linked, and no file content is copied a second time. Entries are created under a temporary name and renamed into place, so a process already running from a file keeps the inode it started with. Directory symlinks in the root (/bin, /lib, /sbin and friends) are written through, not replaced. When the two are on different filesystems, hokuto copies the tree into place with its internal copy instead.

Overrides
HOKUTO_ZSTD_CHUNK_MB=N
force a frame size in MiB; 0 packs single-frame archives the way hokuto did before
HOKUTO_NO_HARDLINK_INSTALL=1
copy files into place instead of hard linking them (for a filesystem that accepts hard links but misbehaves with them)
Library ABI Rebuilds

Every package records the shared libraries it links against in its libdeps file (elf64:libfoo.so.3). When an update removes a library that installed packages link against, hokuto install/update offers to rebuild them. That only covers what is installed on the machine, so the binary mirror index also records each package's libdeps, and hokuto bump --auto --build checks what was published.

  • After the builds, each built package, split outputs included, is compared with its previous package on the mirror. A shared library the new package no longer ships (libfoo.so.3 gone, libfoo.so.4 new) is an ABI change; a library that only moved directory, or a new release that keeps the soname, is not
  • The newest published package of every recipe linked against a removed library gets its revision bumped (1.0 1 becomes 1.0 2). Split packages count for their recipe; the library's own recipe, binary recipes and packages without a recipe are left out
  • The bumped version files are committed, one commit per repository with a message such as rebuild for libfoo (libfoo.so.3) ABI change, and pushed like a version bump. A recipe whose version file has uncommitted changes is skipped with a warning
  • At the end, bump names the libraries and the command that builds the bumped packages: hokuto update --build-missing-binaries, which lists every recipe whose current version or revision has no package yet, or hokuto-builder rebuild in the build container, which first updates the container from the mirror so the rebuilds link against the new library, then builds and uploads. hokuto cross-sync picks up the same revision bumps for aarch64

The libdeps in the index arrived with index metadata version 2. hokuto upload records them for every package it uploads; hokuto upload --reindex fills them in for the packages already on the mirror, reading local packages and downloading the others once. Until then, bump warns how many published packages it could not check.

Git Source Checkouts

Prefix a source URL with git+ to have Hokuto check out a Git repository. Git sources are not included in the checksums file. The checked-out repository is linked into the package source directory and its contents are copied into the temporary build directory before the build script runs.

Source syntax
git+https://github.com/example/project
default branch
git+https://github.com/example/project#2.3.0
raw branch, tag, or revision
git+https://github.com/example/project#545a54...
commit hash
git+https://github.com/example/project#branch=dev
named branch
git+https://github.com/example/project#tag=v2.3.0
named tag
git+https://github.com/example/project#branch=dev&depth=1
shallow branch checkout
git+https://github.com/example/project#tag=v2.3.0&depth=1
shallow tag checkout
git+https://github.com/example/project#depth=1
shallow checkout of the default branch

Shared cache

Normal Git sources use a full bare mirror under /var/cache/hokuto/sources/_cache/git/. Hokuto reuses that object store for packages which use the same repository, updates it with the remote, and creates a shared working checkout under /var/cache/hokuto/sources/_cache/checkouts/. Branch and tag selectors are resolved to their full Git refs, while raw fragments continue to work as branches, tags, or commit revisions.

Each package receives a symbolic link such as /var/cache/hokuto/sources/pkgname/project pointing to the matching shared checkout. Checkout cache keys include the repository URL and selected ref, so different branches or tags do not overwrite one another. Fetching and checkout updates are protected by locks, allowing parallel package operations to safely reuse the same cache.

Shallow checkouts

Add depth=N to download only the requested number of commits. Shallow checkouts bypass the full bare mirror and use a separate checkout keyed by repository URL, ref, and depth. Existing shallow branches are refreshed with a depth-limited fetch, so updating a package does not automatically download the complete history.

  • depth must be a positive integer.
  • Shallow named refs must use branch= or tag=.
  • Arbitrary commit hashes cannot be combined with depth, because servers may refuse to fetch an unadvertised commit into a shallow repository.
  • Shallow checkout support requires the system git client. Hokuto's internal Git fallback remains available for normal, full-history sources only.

To give two checkouts of the same repository different names in the package source cache, use the source filename override: git+https://github.com/example/project#branch=stable -> project-stable.

Build Server (hokuto-builder)

hokuto-builder (package hokuto-tools) runs hokuto in a systemd-nspawn container instead of on the host. Build dependencies and base-devel are installed into the container, so building packages for the mirror never changes the host system. The container uses the host's hokuto, recipes (/repo), binary and source caches, build tmpdirs, signing key, mirror credentials and git identity, so bumps are committed and pushed and packages are signed and uploaded as they would be on the host. Commands run as the invoking user; hokuto-builder asks for sudo itself.

Builds run at idle CPU priority: the container only gets the CPU time the host's own work leaves. They are also capped at 80% of the CPU threads, so the desktop and games always have cores to spare, and their memory use is throttled above half the RAM, before the host's own memory is swapped out.

Commands
hokuto-builder create
create the container (once); asks where to put it
hokuto-builder bump [-y] [-jN]
auto-bump outdated recipes from Repology, build them N at a time and upload them; -y bumps and builds everything without asking
hokuto-builder build <pkg...>
build already bumped packages as bump does, then upload them (--no-upload skips the upload)
hokuto-builder rebuild [-y] [-jN]
build and upload the recipes ahead of the mirror, such as packages bump revision-bumped after a library dropped a soname; -y builds those published before without asking
hokuto-builder cross-sync [-system] [-y] [-jN]

hokuto-builder cycle
one unattended round (see Unattended builds)
hokuto-builder blacklist [list | remove [-arch <arch>] <pkg>... | clear]

hokuto-builder nobuild [list | [add] [-cross] <pkg>... | remove [-cross|-native] <pkg>... | clear [-cross|-native]]

hokuto-builder python-rebuild [--status | --list | --check [-jN] | --confirm [--force] | --cancel]

hokuto-builder run <cmd...>
run a command in the container
hokuto-builder shell

hokuto-builder update

hokuto-builder destroy

hokuto-builder --generic <command>

Only one hokuto-builder command runs at a time (both containers share the binary cache); a second one waits for it. The build commands remove the packages they left installed in the container.

Unattended builds

hokuto-builder.timer keeps the mirror current without anyone at the keyboard. It runs hokuto-builder cycle 2 minutes after it starts, then again 15 minutes after each round ends, so rounds never overlap however long one takes:

sudo systemctl enable --now hokuto-builder.timer

A round runs these steps, each on its own so one failing does not stop the others:

  • bump -y: bump and build what changed upstream
  • rebuild -y: build what the bumps made necessary
  • --generic rebuild -y: the same for the generic packages, when enabled
  • cross-sync -system -y and cross-sync -y: the arm64 packages
  • before each step and at the end, remove what failed builds left in the build tmpdirs, so they cannot fill them for the next step (skipped while any hokuto runs)

Each package's status and log are published to the package index (except generic and cross-system builds, which it does not list). Rounds that built or failed something are listed on Build rounds, and every round in /var/log/hokuto-builder/runs.log; the full output is in journalctl -u hokuto-builder. A round stops before building anything, and the service shows as failed, when a container it needs is missing or a setting is invalid; the timer retries every 15 minutes, so the next round after fixing it just works.

A package whose own build fails in a round is blacklisted for that architecture, so later rounds do not build it again; a package that only failed because a dependency did is not. The entry ends by itself when the recipe's version or revision changes, and hokuto-builder blacklist remove <pkg> retries it sooner. The round that blacklists a package reports it, as it does a Repology project bump could not match to a recipe: such a project needs a name mapping in hokuto's auto-bump (internal/hokuto/pkgdev.go).

The no-build list (/var/db/hokuto/nobuild.json, shared by both containers and the host) is for packages that should not be built here at all, for instance ones too large for the build machine or built elsewhere. Unlike blacklist entries, its entries never expire. hokuto-builder nobuild <pkg> keeps a recipe from being built after a bump and from rebuild; hokuto-builder nobuild -cross <pkg> keeps its aarch64 packages out of cross-sync and cross-sync -system. list, remove and clear work as for the blacklist, with -cross or -native to limit them to one kind of entry. hokuto nobuild is the same command outside the container.

Python upgrades. A new Python minor release (3.14 → 3.15) changes the extension ABI and the site-packages directory, so every package with Python modules or linked against libpython has to be rebuilt, and how many of them build against the new release is only known by trying. When a publishing build (bump --build, hokuto-builder build) builds python with a new minor release, the build server therefore holds it: nothing is bumped, the new python is not uploaded, rebuild and cross-sync leave python alone, and the build pages show a notice.

  1. hokuto-builder python-rebuild --check [-jN] builds and installs the new python and builds every package that needs the rebuild against it, the Python build tools and meson first. It runs in a throwaway overlay of the container, so nothing it installs stays, and nothing is uploaded. It reports which packages fail and updates the notice.
  2. Fix what failed and check again, or revert the python bump and drop the hold with --cancel.
  3. hokuto-builder python-rebuild --confirm, once every package built, bumps their revisions, commits and pushes them, and releases python. --force confirms without a passed check.
  4. The next hokuto-builder rebuild (or round) builds python and the bumped packages and publishes them together; cross-sync then does the same for aarch64.

--status shows the held upgrade and the last check, --list the packages it rebuilds: the recipes marked python-rebuild and those of the published packages linked against the old libpython.

Configuration

Settings are in /etc/hokuto-builder.conf, one KEY=value per line:

ROOTFS, GENERIC_ROOTFS
where the containers are; saved by create
BUILD_USER
the user the service builds as; saved by create
CYCLE_GENERIC=0
set to 1 to have each round also run --generic rebuild -y; the generic container must exist
CYCLE_JOBS=4
packages a round builds at once
CPU_WEIGHT=idle
the container's CPU priority (systemd CPUWeight=, 1-10000 or idle); empty removes the limit
CPU_QUOTA
the container's CPU cap (systemd CPUQuota=, 100% per thread, so 1600% is 16 threads); unset, 80% of the threads; empty removes the cap
MEMORY_HIGH=50%
where the container's memory is throttled (systemd MemoryHigh=, bytes or a percentage of RAM); empty removes the limit

For example, to build the generic packages too:

echo CYCLE_GENERIC=1 | sudo tee -a /etc/hokuto-builder.conf

Alternative dependencies

Unattended builds cannot answer which package should satisfy a dependency such as xlibre | xorg-server. List the package to pick in /etc/hokuto/hokuto.prefer, which the container copies from the host on every run: when none of the alternatives is installed, the first one listed there is chosen without asking.

echo xlibre | sudo tee -a /etc/hokuto/hokuto.prefer

Skipped packages

Packages bump should leave alone are listed in /var/db/hokuto/bump-ignore.json, and packages rebuild should skip in /var/db/hokuto/build-ignore.json (build-ignore-generic.json for the generic container); a rebuild entry is dropped once the recipe's version or revision changes.
