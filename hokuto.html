hokuto package manager

Package Manager written in Go with minimal optional external dependencies:

  • b3sum
  • git
  • lzip
  • rsync
  • tar
  • wget
  • zstd

The package manager is fully functional without any external dependencies (except for git checkouts) if executed as root.

Usage

hokuto help for basic usage
hokuto function for advanced options

Configuration Files

Configuration files are stored in /etc/hokuto/

  • hokuto.conf: global config file
  • hokuto.lock: pin a package to specific version (pkgname version)
  • hokuto.pkgset: pkgsets for batch updates (hokuto bump -set setname oldver newver)
  • hokuto.rebuild: simple DKMS (triggerpackage package1 package2)
  • hokuto.update: sets package build priority on updates (package1 package2 package3)
  • /etc/hokuto/keys/foo.key: key used to sign packages (use hokuto settings to generate a new key)

Package Structure

  • build: bash file with build instructions
    Available env variables in the script:
    $1: build DESTDIR
    $2: package version
    $3: package name
    $HOKUTO_ARCH: build arch (aarch64 or x86_64)
    $HOKUTO_CROSS: (1 or 0) and $HOKUTO_CARCH (arm64)
    $HOKUTO_CROSS_SYSTEM: (1 or 0) set when building the cross-system toolchain (-cross=arm64,system)
    $CROSS_PREFIX: prefix the build should install into; /usr for native and plain cross builds, /usr/<triplet> for cross-system builds. The usual idiom is PREFIX="${CROSS_PREFIX:-/usr}"
    $HOKUTO_LTO: whether LTO is enabled for the current build (1 or 0)
    $MULTILIB: (1 or 0)
    $HOKUTO_ROOT: rootdir, usually / but can be set to another dir
    $TMPDIR: current tmpdir
    $HOKUTO_BUILD_DIR: current build dir path
    $HOKUTO_REAL_USER: user that executed hokuto (allows installation in user home directory) $HOKUTO_SPLIT_DIR: split dir output (split packages generation)
  • checksums: b3sums of source files
  • depends{.supackage}: dependencies
    • pkgname: runtime/build dependency
    • pkgname==17.*: require any release from major version 17
    • pkgname make: build dependency
    • pkgname makeopt: optional binary-only build dependency. Hokuto uses an installed package or installs an available binary version for the build, but continues without it when no binary is available. Packages installed only for the build are removed afterward
    • pkgname optional: package will be automatically rebuilt once the dependency is available (solves circular deps)
    • pkgname runtime: runtime only dependency
    • pkgname suggest "comment": suggested optional dependency
    • pkgname rebuild: forces rebuild of package even if already installed, only enabled with -rebuilds build command flag
    • pkgname cross: cross (arm64) runtime dependency, e.g. aarch64-zlib-ng cross as a dependency of file pulls in aarch64-zlib-ng whenever aarch64-file is built/installed, and it stays a real (always-verified) dependency afterward, same as a plain dependency line but scoped to cross builds
    • pkgname cross make: cross (arm64) build-time-only dependency; only needed while building the cross target, not required once it's installed (e.g. aarch64-gcc cross make)
    • Prefixed vs bare cross dependencies. A cross dependency whose name carries the target arch prefix (aarch64-gcc cross make, aarch64-libelf cross make) is a target artifact, built for the target and installed into the sysroot. A cross dependency with a bare name (mercurial cross make, cmake cross make) is a host tool the cross build needs and is built/installed natively — use this when there is no sensible aarch64-* counterpart. A cross dependency naming a different architecture (x86_64-gcc cross make while targeting arm64) is ignored, so one depends file can list several targets
    • pkgname crossnative: like cross, but skipped when building the cross-system toolchain itself (-cross=arm64,system)
    • pkgname crossnative make: like cross make, but skipped when building the cross-system toolchain itself
    • Cross builds only honor cross dependencies. Under -cross=<arch> (with or without ,system) every dependency line that is neither tagged cross/crossnative nor already carries the target arch prefix (aarch64-*) is ignored, including plain make dependencies. Those lines describe the native build of the package; a cross build must declare what it needs explicitly. So a recipe that needs e.g. pahole for both builds lists it twice: pahole make for native and pahole cross make for cross
    • == <> => <= version (eg ffmpeg<=7.2.0): dependency version constraints. hokuto can build older versions by fetching the package from the repo git history
    • package1 | package2: hokuto will prompt which dependency to use
  • equivalents (repository root): mutually exclusive, dependency-compatible package pairs, one pair per line as upstream-package replacement-package. Either installed package satisfies an unconstrained dependency on the other. Installing one replaces the other, and generated library dependencies use an ordered replacement | upstream alternative for replacement packages. Version-constrained dependencies remain exact. The relevant pair is embedded in built packages so replacement also works when installing exclusively from a binary mirror
  • options:
    asroot: build package as root
    binary: binary package with bundled deps, ignored by automatic dependency resolver and built without base-devel
    clang: sets flto=auto for clang builds
    cross: the recipe is prepared for cross builds. Only needed when that cannot be seen from the recipe itself, e.g. an arch-independent package, or one that needs no changes at all
    cross-simple: use the native host compiler instead of the cross-compiler
    devel: install base-devel for a binary or nodevel package that explicitly requires build tools
    host-tool: don't modify the PATH in the build env to include the cross-toolchain binaries
    interactive: shows build output log and allows interactive scripts
    nocross: never cross build this package, whatever the recipe looks like
    nocrossopt: don't enable CFLAGS_ARM64 for cross builds
    nodevel: don't install base-devel packages for this build
    noram: build in TMPDIR2
    nolto: disable LTO
    nostrip: disable stripping
    staticlibs: keep static libraries
    options.subpackage: use staticlibs/!staticlibs or nostrip/!nostrip to enable or disable overrides for a split package
  • files: local package files
  • libdeps.ignore{.subpackage}: ignore dependency during auto dependency resolution
  • post-install: bash script executed after package install
  • .sources: source links with substitutions
    • ${version}: The raw version from the version file.
    • ${version-clean}: Version with underscores (_) replaced by dots (.) (e.g., 1_2_3-1 → 1.2.3-1).
    • ${version-undertomid}: Version with underscores (_) replaced by dashes (-) (e.g., 6.1.2_1 → 6.1.2-1).
    • ${version_}: Version with dots (.) replaced by underscores (_).
    • ${version-}: Version with dots (.) replaced by dashes (-).
    • ${version-major}: 1.2.3 -> 1
    • ${version-major-minor}: 1.2.3 -> 1.2
    • ${version-sqlite}: custom substitution for sqlite download links
    • ${version-glued}: 1.2.3 -> 123
    • ${version-glued-end}: 1.2.3 -> 1.23
    • ${version-last-only}: 1.2.3.sdk102 -> sdk102
    • ${pkgname}: The name of the package.
  • sources: source links with substitutions replaced with actual links (for repology parsing)
  • version: version revision

Cross Build Support

Cross building a recipe that was never adapted for it rarely fails outright. Configure scripts fall back to host defaults, the build picks up the host's headers and libraries, and the result looks like a package right up until something links against it or it is installed on the target. Hokuto therefore refuses such a build instead of producing one.

A recipe counts as prepared for cross builds when any of these is true:

  • its options file contains cross
  • its build script branches on the cross environment, that is it mentions CROSS_PREFIX, HOKUTO_CROSS or CROSS_COMPILE outside a comment
  • its depends file declares cross or crossnative dependencies

Both of the last two are needed because neither is sufficient on its own: low level packages such as brotli and gmp handle CROSS_PREFIX but have too few dependencies for any of them to be marked cross, while shadow and linux-rpi4 carry cross dependencies without naming hokuto's variables in their script.

options wins over what the recipe looks like, in both directions: cross marks a recipe that needs no changes (an arch-independent or data-only package, for instance), and nocross holds one back that would otherwise pass. The check applies to both -cross=<arch> and -cross=<arch>,system, and not to plain build dependencies that are compiled natively during a cross session.

To build an unprepared recipe anyway, while adapting it:
HOKUTO_ALLOW_UNCONFIGURED_CROSS=1 hokuto build -cross=arm64 pkgname

Binary Packages

A binary package is an ordinary .tar.zst, readable by tar --zstd -xf and any zstd implementation. It is compressed as a series of independent zstd frames rather than one, which is what lets hokuto decompress it on several cores when installing; a single frame can only ever be decoded by one.

The frame size is chosen from the size of the package so that it lands on about half the machine's cores, clamped between 32 MiB and 256 MiB. Cutting the stream costs a little compression ratio, because matches can no longer reach back across a frame boundary, and the clamps keep that in the region of a fraction of a percent for large packages. A package small enough to fit in one frame is compressed exactly as it was before.

Installing unpacks into a staging directory and then moves the tree into place. When staging and the target root are on the same filesystem, that move is done with hard links: mode, ownership, timestamps, xattrs and ACLs come along with the inode, files hard linked to each other inside the package stay linked, and no file content is copied a second time. Entries are created under a temporary name and renamed into place, so a process already running from a file keeps the inode it started with. Directory symlinks in the root (/bin, /lib, /sbin and friends) are written through, not replaced. Hokuto falls back to rsync when the two are on different filesystems.

Overrides:
HOKUTO_ZSTD_CHUNK_MB=N: force a frame size in MiB; 0 packs single-frame archives the way hokuto did before
HOKUTO_NO_HARDLINK_INSTALL=1: place files with rsync instead of hard links

Git Source Checkouts

Prefix a source URL with git+ to have Hokuto check out a Git repository. Git sources are not included in the checksums file. The checked-out repository is linked into the package source directory and its contents are copied into the temporary build directory before the build script runs.

Source syntax:
git+https://github.com/example/project — default branch
git+https://github.com/example/project#2.3.0 — raw branch, tag, or revision
git+https://github.com/example/project#545a54... — commit hash
git+https://github.com/example/project#branch=dev — named branch
git+https://github.com/example/project#tag=v2.3.0 — named tag
git+https://github.com/example/project#branch=dev&depth=1 — shallow branch checkout
git+https://github.com/example/project#tag=v2.3.0&depth=1 — shallow tag checkout
git+https://github.com/example/project#depth=1 — shallow checkout of the default branch

Shared cache

Normal Git sources use a full bare mirror under /var/cache/hokuto/sources/_cache/git/. Hokuto reuses that object store for packages which use the same repository, updates it with the remote, and creates a shared working checkout under /var/cache/hokuto/sources/_cache/checkouts/. Branch and tag selectors are resolved to their full Git refs, while raw fragments continue to work as branches, tags, or commit revisions.

Each package receives a symbolic link such as /var/cache/hokuto/sources/pkgname/project pointing to the matching shared checkout. Checkout cache keys include the repository URL and selected ref, so different branches or tags do not overwrite one another. Fetching and checkout updates are protected by locks, allowing parallel package operations to safely reuse the same cache.

Shallow checkouts

Add depth=N to download only the requested number of commits. Shallow checkouts bypass the full bare mirror and use a separate checkout keyed by repository URL, ref, and depth. Existing shallow branches are refreshed with a depth-limited fetch, so updating a package does not automatically download the complete history.

  • depth must be a positive integer.
  • Shallow named refs must use branch= or tag=.
  • Arbitrary commit hashes cannot be combined with depth, because servers may refuse to fetch an unadvertised commit into a shallow repository.
  • Shallow checkout support requires the system git client. Hokuto's internal Git fallback remains available for normal, full-history sources only.

To give two checkouts of the same repository different names in the package source cache, use the source filename override: git+https://github.com/example/project#branch=stable -> project-stable.
